总纲：LLM 应用的本质是一个函数

第一性原理 · 为什么要“编程”而不是“写提示词”

传统提示词工程靠手工试错：改提示词、看结果、再改。语言模型对提示词非常敏感，稍微改动输出就不同。开发 LM 应用时，常要测试大量变体，过程困难、耗时、难维护。

第一性原理

如果 LLM 调用本质上是一个函数，那我们就应该用定义函数的方式去定义它——声明输入输出类型，然后让框架负责“怎么调用”。

这就是 DSPy 反复强调的那句话：Program, don't prompt.

传统提示词工程DSPy 程序
手写一段字符串声明 输入 -> 输出
手动调整措辞框架自动生成提示词
换模型要重写签名不变，换 LM 即可
无法系统优化用优化器自动搜索更好的提示

DSPy 名称含义

  • Declarative / 声明式：声明想做什么，而不是提供具体提示词。
  • Self-improving / 自我改进：自动改进生成的提示词。
  • Python：用 Python 开发。

苦涩的教训

Richard Sutton《The Bitter Lesson》：利用计算的通用方法最终最有效，而且优势很大。长期看，真正重要的是利用计算。

AI 的最佳做法通常是让应用搜索解空间，自己学习。提示词开发也如此：自动搜索和学习的系统最终会比手工提示词工程更有效。

推荐开发流程

  1. 创建简单基线应用；
  2. 评估基线；
  3. 优化应用；
  4. 满意后投入生产。

签名（Signature）：声明“要什么”

接口隔离 · 把 what 和 how 分开

官网的起始代码只有四行：

import dspy

lm = dspy.LM("openai/gpt-4o-mini")
dspy.configure(lm=lm)

haiku_signature = "subject -> haiku"
haiku_generator = dspy.Predict(haiku_signature)
result = haiku_generator(subject="computer science")
print(result.haiku)
1

签名（Signature）——声明“要什么”

haiku_signature = "subject -> haiku"

这行代码定义了一个签名。签名就是 DSPy 里的“函数声明”——它不关心怎么实现，只关心输入和输出是什么。字符串 "subject -> haiku" 被 DSPy 解析成一个签名类，输入字段 subject 和输出字段 haiku 默认都是字符串类型。

第一性原理

签名只描述 what，不描述 how。这一步是在做接口隔离。

命名的重要性

变量名本身就是给模型的提示。如果你把 haiku 改成 limerick，模型就会写一首打油诗而不是俳句，输出字段也会变成 result.limerick。

2

模块（Module）——决定“怎么做”

haiku_generator = dspy.Predict(haiku_signature)

dspy.Predict 是一个模块。如果说签名是“函数声明”，那模块就是“函数实现策略”。

执行 dspy.Predict(haiku_signature) 时，DSPy 在后台做了三件事：

  1. 把字符串签名解析成 Signature 类。
  2. 自动生成默认指令。对于 subject -> haiku，默认指令是 "Given the fields subject, produce the fields haiku."
  3. 实例化一个 Predict 模块。
3

调用——背后到底发生了什么

当你调用 haiku_generator(subject="computer science")，DSPy 的运行时开始工作：

  1. 检查 LM 配置：确认已设置默认语言模型。
  2. Adapter 渲染：用 ChatAdapter 把签名、指令、输入渲染成 LLM 能消费的消息格式。
  3. 构建提示词：把指令、字段 schema、格式说明和输入值拼成完整提示词。
  4. 调用 LLM：消息发给 LLM，默认开启缓存。
  5. 解析响应：从返回文本中提取输出字段。
  6. 返回 Prediction：返回 Prediction 对象。
  7. 记录历史：可用 dspy.inspect_history(n=1) 查看完整提示词和响应。
核心洞察

你写的是四行 Python，但背后跑的是一个完整的提示词编译管道——指令生成可替换、Adapter 可替换、缓存可配置、历史可检查。

类签名：信息分层的艺术

当字符串签名的表达能力不够时

第一性原理

字符串签名有“能力边界”：无法附加语义说明、无法约束取值类型、无法撰写独立任务指令。类签名就是为解决这三个“无处安放”而存在的。

类签名的四层结构

from typing import Literal
import dspy

class HaikuBot(dspy.Signature):
    """Write a haiku about the given subject, using evocative imagery."""

    location: str = dspy.InputField(desc="The place the haiku should evoke")
    season: Literal["spring", "summer", "autumn", "winter"] = dspy.InputField()
    mood: str = dspy.InputField()
    haiku: str = dspy.OutputField(desc="A 5-7-5 syllable poem")
层级写什么优化器是否可改第一性原理角色
类名语义化命名否代码可读性
Docstring任务意图、语气、高层指导是可优化的指令变量
字段名输入输出的语义角色否不可变锚点
字段类型str、bool、Literal、Pydantic 约束否运行时契约
字段 desc字段级的补充说明否不可变锚点
关键设计决策

优化器可以改写 docstring，但不会碰字段名和 desc。这意味着字段名选得不好，优化器无法帮你修正。这个区分决定了你的注意力分配：字段名要反复斟酌，docstring 可以大胆写，让优化器去改。

类型约束：把提示词中的约束变成类型系统中的约束

Literal 把 season 字段锁定在四个值上。DSPy 底层用的是 Pydantic，每一个字段都是一个 Pydantic FieldInfo。这意味着任何 Pydantic 约束都可以用：gt、lt、min_length、max_length 等。

第一性原理

在传统提示词工程里，“season 必须是这四个之一”是一个建议；在 DSPy 里，Literal 是一个运行时会强制执行的契约。

Docstring 和 Module 的分工

设计原则

Instructions live on the signature, not the module. 签名管“做什么”，模块管“怎么做”。同一个签名可以交给 Predict、ChainOfThought、ReAct 中的任何一个。

更换模块：从 Predict 到 ChainOfThought

一行代码的变化，背后是装饰器模式

代码变化极其克制：

# 之前
haiku_generator = dspy.Predict(HaikuBot)

# 之后
reasoning_haiku_bot = dspy.ChainOfThought(HaikuBot)

签名 HaikuBot 一个字没改。函数调用完全一致。唯一区别是模块从 Predict 变成了 ChainOfThought。

幕后机制：DSPy 对签名做了什么

ChainOfThought 在初始化时，接收 HaikuBot 作为基础签名，然后在内存中构造一个新的签名对象。这个新签名继承了你 HaikuBot 的全部内容，但在前面插入了一个额外的输出字段：reasoning。

第一性原理

这是装饰器模式在签名层面的应用。签名没有被替换，而是被包裹了一层。基础契约完全保留，只是多了一个中间产物：推理过程。

reasoning 字段的意义

新签名多出的 reasoning 输出字段，被 DSPy 自动放置在 haiku 输出字段之前。模型被要求先产出推理文本，再产出俳句。

reasoning 不是一个“答案字段”，它是一个过程字段。它的存在改变了模型的生成轨迹——从“直接输出答案”变成“先展开推理，再收敛到答案”。

模块层的灵活性

模块对签名的操作执行结构
Predict原样使用单步生成
ChainOfThought运行时插入 reasoning 字段单步推理后生成
ProgramOfThought生成并执行 Python 代码代码执行
BestOfN多次采样，选最佳多候选
核心洞察

模块对签名的“修改”是运行时行为，不是代码修改。你写的 HaikuBot 是一个纯净的接口声明。策略可以随时替换，接口本身毫发无损。

ReAct 与工具：给程序装上手和脚

从“想”到“做”的质变

第一性原理

语言模型的知识是冻结的、近似的、不可验证的。当模型的知识不足以支撑一个可靠输出时，给它一个“去做点什么”的出口。

工具：就是一个普通的 Python 函数

import wikipedia

def wikipedia_search(query: str) -> list[str]:
    """Search Wikipedia for the given query and return a list of page titles."""
    return wikipedia.search(query)

def get_wikipedia_page(title: str) -> str:
    """Fetch the full content of a Wikipedia page given its title."""
    return wikipedia.page(title).content

没有任何装饰器，没有任何继承，没有任何特殊标记。DSPy 读的是三样东西：函数名、参数名和类型、docstring。

第一性原理

工具不是“DSPy 特有的东西”，而是DSPy 对普通 Python 函数的一次语义解读。任何你已有的 Python 函数，加上类型提示和 docstring，就是一个 DSPy 工具。

ReAct：一个“推理-行动”循环

haiku_bot = dspy.ReAct(
    HaikuBot,
    tools=[wikipedia_search, get_wikipedia_page],
    max_iters=4
)

循环的四个步骤：

  1. 推理：模型看到任务和可用工具列表，思考“我现在需要做什么？”
  2. 行动：模型选择一个工具，填入参数，调用它。
  3. 观察：工具返回结果，模型看到这个结果。
  4. 判断：信息够了吗？够了就调用 finish，不够就回到第 1 步。
关键细节

循环次数是模型自己决定的。有些任务需要多次搜索，有些任务模型觉得不需要查证就能做。max_iters=4 只是一个安全上限，防止模型陷入无限循环。

finish：一个特殊的内置工具

你只定义了两个工具，但模型实际看到的是三个。finish 是 ReAct 自动注入的，它告诉模型：“当你觉得信息足够了，调用这个工具来结束循环。”

第一性原理

finish 的存在把“是否继续”这个决策显式化了。只要模型没调用 finish，循环就继续。

trajectory：循环的“黑匣子记录”

result = haiku_bot(location="Camp Meeker", mood="pensive", season="summer")
print(result.trajectory)

trajectory 里记录了每一次“推理 → 调用 → 观察”的完整序列。前两个模块是单步的，ReAct 是多步的，中间状态变得重要。trajectory 就是 DSPy 为多步程序提供的可观测性机制。

模块对签名的操作执行结构能力边界
Predict原样使用单步生成只能依赖内部知识
ChainOfThought插入 reasoning单步推理后生成推理更充分，但仍封闭
ReAct注入 finish多步循环可以获取外部信息

组合模块：构建复杂 AI 系统的心法

模块是可组合的积木

第一性原理

ReAct 本身就是由 Predict 和 ChainOfThought 组合而成的。模块是构建块，它们本身就是为组合而生的。dspy.Module 就是 DSPy 世界里的“组合单元”。

dspy.Module 的契约

构建自定义模块需要实现两个函数：

  • __init__()：设置初始状态，并定义子模块。
  • forward()：处理调用时的逻辑，让数据流经子模块。

为什么是这两个函数？框架通过遍历 self.__dict__ 来发现子模块（用于优化器搜索、序列化）。forward 是运行时逻辑的“包裹”位置。这种分离确保了优化器能看到什么和实际运行时发生什么不会混淆。

示例：HaikuEnsemble

class HaikuEnsemble(dspy.Module):
    def __init__(self, num_candidates=3):
        super().__init__()
        self.writer = dspy.ChainOfThought(HaikuWriter)
        self.judge = dspy.ChainOfThought(HaikuJudge)
        self.num_candidates = num_candidates

    def forward(self, location, mood, season):
        candidates = []
        for _ in range(self.num_candidates):
            result = self.writer(
                location=location, mood=mood, season=season, num_haikus=1
            )
            candidates.append(result.haiku)

        with dspy.context(lm=judge_lm):
            best = self.judge(
                location=location, mood=mood, season=season,
                candidate_haikus=candidates
            )
        return dspy.Prediction(haiku=best.selected_haiku, reasoning=best.reasoning)
关键点

writer 和 judge 是 Parameter（会被优化器发现）；num_candidates 是普通属性（不会被优化器搜索）；forward 里是纯 Python 逻辑，没有任何 DSPy 特有的“链式 API”。

为什么分解模块？

理由核心原则
隔离上下文关注点分离，避免无关信息污染
可复用组件研究子模块可协助任何需要依据的程序
成本优化简单工作路由到便宜模型，最终撰写用强模型
隔离变量精确定位是哪个模块出了问题
核心洞察

你写的不是提示词，你写的是 AI 程序的架构。签名定义接口，模块定义执行策略，dspy.Module 让你把这些组件组合成任意复杂的系统。

指标（Metrics）：定义“更好”

优化器的方向感

第一性原理

所有优化器共享一个循环：“run your program many times, keep the version that scores best.”要让“更好”这个判断成立，你必须先定义什么叫“更好”。没有指标，优化器就是在黑暗中随机搜索。

指标的契约

def my_metric(example, prediction, trace=None):
    return prediction.answer == example.answer

DSPy 指标是鸭子类型的——没有基类要继承，没有装饰器要注册。任何可调用的对象，只要接收 (gold, pred, ...) 并返回一个分数，就是合法的指标。

三种指标模式

模式一：标注数据对比

def exact_match(example, prediction, trace=None):
    return example.answer == prediction.answer

模式二：规则检查

def haiku_rule_metric(example, prediction, trace=None):
    score = 0.0
    lines = prediction.haiku.split("\n")
    if len(lines) == 3:
        score += 0.3
    if prediction.season.lower() in prediction.haiku.lower():
        score += 0.4
    if prediction.mood.lower() in prediction.haiku.lower():
        score += 0.3
    return score

模式三：LLM-as-judge

class HaikuJudge(dspy.Signature):
    """Rate how well the haiku evokes the given location, season, and mood."""
    location: str = dspy.InputField()
    season: str = dspy.InputField()
    mood: str = dspy.InputField()
    haiku: str = dspy.InputField()
    score: float = dspy.OutputField(desc="0.0 to 1.0")

judge = dspy.Predict(HaikuJudge)

数据：dspy.Example 与 .with_inputs()

example = dspy.Example({
    "location": "Bodega Bay",
    "season": "autumn",
    "mood": "mysterious",
    "haiku": "..."
}).with_inputs("location", "season", "mood")
第一性原理

.with_inputs() 划定了程序能看到的和指标能看到的之间的边界。程序只看输入字段，指标可以看全部字段。这个分离防止了数据泄漏。

运行基线评估

evaluator = dspy.Evaluate(
    devset=dev_set,
    metric=haiku_rule_metric,
    num_threads=10,
    display_progress=True
)

results = evaluator(haiku_bot)
print(results.score)
基线信号

官网实测：dspy.ReAct 俳句生成器在规则指标上只得了 30%。模型不知道你关心音节数、季节词的逐字出现。30% 的基线，恰恰证明了指标的区分度。

高级设计：trace 与 feedback

trace：优化时会被填充，让指标看到程序是怎么到达这个答案的。评估时返回连续分数，优化时返回二值化信号。

feedback：指标可以返回 dspy.Prediction(score, feedback)。score 被 Evaluate 平均，feedback 被 GEPA 的反思循环读取。

第一性原理

分数是标量信号，反馈是自然语言信号。GEPA 不只用分数来搜索，还用“为什么这个答案不好”的文本解释来指导搜索方向。这让优化从“盲搜”变成了“有指导的搜索”。

GEPA 优化：让程序自己写提示词

反思驱动的进化

第一性原理

手工调优的搜索空间是无限的，而人类的试错能力是有限的。优化器的任务，就是用自动化的方式在这个无限空间中进行有方向的搜索。

配置优化器

optimizer = dspy.GEPA(
    metric=haiku_metric,
    reflection_lm=dspy.LM("openai/gpt-5.4", temperature=1.0),
    auto="light",
    num_threads=2
)
optimized_haiku_bot = optimizer.compile(haiku_bot, trainset=train, valset=val)
配置项设计决策第一性原理
reflection_lm 反思模型与任务模型分离 关注点分离：执行要便宜快速，反思要强大
auto 预算的预设 在探索与成本之间做权衡
trainset / valset 训练/验证分离 防止过拟合

GEPA 的内部循环

GEPA 的执行循环：

  1. 用学生 LM 在训练样本上执行程序，用指标打分。
  2. 将样本和指标结果发送给反思 LM，由它提出新指令。
  3. 用新指令再次运行程序，再次打分，保留得分最好的候选。
  4. 循环重复，直到预算耗尽。
Pareto 前沿采样

GEPA 维护了每个样本上的最佳表现者。如果候选 A 在“秋季俳句”上最好，候选 B 在“夏季俳句”上最好，两者都会留在 Pareto 前沿上，都有机会被选中进行变异。这避免了“为了提升平均分而牺牲特定场景”的陷阱。

逐预测器反思

GEPA 的反思是逐预测器进行的。对于每个需要更新的预测器，GEPA 会调用指标两次——一次在模块级别获取聚合分数，一次在预测器级别获取该步骤的孤立评分。这样，反思模型可以看到“是哪个子模块出了问题”。

结果：小模型超越大模型

实测结果

gpt-5.4-nano（小模型）+ GEPA 优化 = 90.1%
gpt-5.4（大模型）未优化 = 82.4%

小模型经过优化后，不仅超过了自身基线（78.1% → 90.1%），还超过了未优化的大模型。

第一性原理

大模型的优势在于“通用能力”，但提示词优化带来的“任务特定能力”可以弥补甚至超过这个差距。同一个程序、同一个指标、同一组数据，在不同的任务模型上会收敛到不同的最优提示词。

保存与加载：把优化成果变成资产

程序 = 结构 + 状态

第一性原理

经过 GEPA 优化后，程序有了两样东西：结构（你写的 Python 类定义）和状态（优化器学到的成果）。这两样东西的生命周期不同——结构走 Git，状态需要独立保存和传递。

两种保存模式

状态模式（JSON）——你通常需要的

optimized_haiku_bot.save("optimized_haiku_bot.json")

加载时先实例化程序，再调用 .load()：

haiku_bot = dspy.ReAct(HaikuBot, tools=[...])
haiku_bot.load("optimized_haiku_bot.json")
第一性原理

状态是数据，不是代码。JSON 文件里装的是优化后的指令文本和示例列表。你加载的 JSON 文件里没有可执行代码——结构来自代码库，状态来自 JSON，两者分离，互不污染。

安全警告

整包模式的目录包含可执行 Python，只从你信任的来源加载程序。这是便利性与安全性的权衡。

核心洞察

你保存的不是代码，是程序学到的知识。代码定义程序能做什么，状态定义程序知道怎么做。两者分离，各自用最适合的方式管理。

全景总结：DSPy 工作流的六个阶段

从写提示词到管理优化成果

#阶段核心概念第一性原理
1 签名 Predict + "in -> out" 接口隔离：声明 what，不写 how
2 类签名 Docstring、字段类型、desc 信息分层：可优化的 vs 不可变的
3 更换模块 ChainOfThought 装饰器模式：签名保持纯净，策略运行时扩展
4 工具与 ReAct 普通 Python 函数 + 循环 开放系统：从“想”到“做”
5 组合模块 dspy.Module 嵌套 可组合积木：分解、复用、治理、优化
6 指标与优化 metric → GEPA 定义方向，自动搜索
7 保存与加载 .save() / .load() 结构 vs 状态分离
终极心法

你写的不是提示词，你写的是一个可以用程序方式编译和优化的 LLM 应用。

签名定义每个组件的接口，模块定义执行策略，dspy.Module 让你把这些组件组合成任意复杂的系统，指标定义“更好”，优化器自动搜索最优配置，保存让成果成为可复用的资产。

最佳实践清单

  1. 先基线，再评估，再优化。不要一上来就调 GEPA。
  2. 字段名要反复斟酌。优化器不会碰它，但它是模型理解任务的关键线索。
  3. Docstring 写意图，不写操作手册。具体步骤留给模块和优化器。
  4. 分解复杂程序。隔离上下文、复用组件、路由模型、定位问题。
  5. 指标要有区分度。30% 的基线比 95% 的基线更能暴露问题。
  6. 用独立测试集做最终评估。优化用 valset，生产判断用 testset。
  7. 多试优化器。GEPA 最强但最贵，SIMBA、MIPROv2 各有适用场景。
  8. 状态用 JSON，交付用 Pickle。安全与便利，按场景选择。
