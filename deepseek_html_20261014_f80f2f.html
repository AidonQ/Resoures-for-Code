一周后你要达到的能力标准

你不需要成为 DSPy 工程师，而要成为 DSPy 架构师 + 验收者 + 纠错者

核心定位

你的核心能力不是背 API，而是：知道 DSPy 的功能边界，能画出架构，能定义签名和指标，能指挥 agent 写代码，能看懂中间结果并纠错。这就是“得意忘形”——忘掉具体 API 细节，留下第一性原理和架构判断力。

  1. 能画架构画布：任务 → 签名 → 模块 → 工具 → 数据 → 指标 → 优化器 → 保存。
  2. 能定义签名：输入输出字段、类签名、docstring、字段类型、Literal、desc。
  3. 能选模块：Predict、ChainOfThought、ReAct、自定义 dspy.Module。
  4. 能定指标：dspy.Example、.with_inputs()、Evaluate、metric、trace、feedback。
  5. 能选优化器：BootstrapFewShot、MIPROv2、GEPA，知道成本与适用场景。
  6. 能看中间结果：lm.inspect_history()、result.trajectory、Evaluate.results、get_lm_usage()、保存后的 JSON。
  7. 能纠错：定位是签名、模块、指标、数据、优化器还是 LM 配置的问题。
  8. 能指挥 agent：给架构画布和约束，让 agent 生成代码，你审查并迭代。

核心学习原则

一周学习的方向盘

五条原则

第一性原理驱动：每天先问“这个组件解决什么根本问题”，再看 API。

项目驱动：一周只做一个端到端项目，不要碎片化。

中间结果优先：每跑一步，必须看提示词、轨迹、逐条评估结果。

agent 协作：你写架构和验收标准，agent 写代码；你负责纠错。

得意忘形：不背 API，记住模式——签名声明 what，模块定义 how，指标定义 better，优化器自动搜索。

七天学习路径

每天 3–5 小时，周末 5–6 小时

1

建立第一性原理与最小闭环

核心问题：LLM 应用为什么是一个函数？DSPy 如何把提示词变成程序？

学什么

  • 官网 Getting Started 的 first program。
  • 第一性原理：签名 = 函数声明；模块 = 执行策略。
  • 最小代码：dspy.LM、dspy.configure、dspy.Predict、inspect_history。

做什么

  1. 跑通 dspy.Predict("question -> answer")。
  2. 打印 lm.inspect_history(n=1)，看 DSPy 自动生成的提示词。
  3. 改字段名，观察提示词和输出变化。

产出

一页笔记：DSPy 四行代码背后发生了什么。

检验

你能解释“为什么没写提示词，DSPy 却生成了提示词”。

2

签名深入与模块选择

核心问题：字符串签名不够时，类签名如何信息分层？

学什么

  • 类签名：docstring、字段类型、Literal、desc。
  • 模块：Predict vs ChainOfThought。
  • 关键原则：指令在签名上，不在模块上；优化器改 docstring，不碰字段名和 desc。

做什么

  1. 把 Day 1 的字符串签名升级为类签名。
  2. 加 Literal 约束和 desc。
  3. 换 ChainOfThought，看 reasoning 字段。
  4. 让 agent 生成代码，你只审查签名设计。

产出

一个类签名 + 两个模块对比结果。

检验

你能说出哪些信息可被优化器改，哪些是你必须精确控制的锚点。

3

组合模块、工具与 ReAct

核心问题：如何从“单步生成”走向“多步闭环”？

学什么

  • 自定义 dspy.Module：__init__ + forward。
  • 工具：普通 Python 函数 + 类型提示 + docstring。
  • dspy.ReAct：推理-行动循环，finish，trajectory。
  • dspy.context() 做模型路由。

做什么

  1. 构建一个自定义 Module：两个子模块串联。
  2. 加一个工具，用 ReAct 调用。
  3. 打印 result.trajectory，看每一步 thought、tool、observation。
  4. 让 agent 生成 RAG 或客服 agent 骨架，你检查 forward 数据流。

产出

一张架构图：输入 → 子模块 → 工具 → 输出。

检验

你能从 trajectory 判断模型为什么调用了错误的工具。

4

指标与评估——定义“更好”

核心问题：没有指标，优化器就是盲搜。

学什么

  • dspy.Example、.with_inputs()。
  • metric(example, prediction, trace=None)。
  • dspy.Evaluate、num_threads、display_table。
  • trace 和 feedback 的作用。

做什么

  1. 准备 20–50 条业务数据，转成 Example。
  2. 写一个业务指标：分类准确率、规则检查或 LLM-as-judge。
  3. 跑基线 Evaluate，看逐条失败案例。
  4. 让 agent 插入调试语句，打印 results.results。

产出

基线分数 + 失败案例清单。

检验

你能判断指标是否有区分度，是否数据泄漏。

5

优化器与 GEPA

核心问题：如何让程序自动写更好的提示词？

学什么

  • LabeledFewShot、BootstrapFewShot、MIPROv2、GEPA。
  • GEPA 的 reflection_lm、auto、trainset/valset、feedback、Pareto。
  • 保存与加载：JSON 状态 vs Pickle 整包。

做什么

  1. 用 BootstrapFewShot 跑一次优化。
  2. 用 MIPROv2 或 GEPA 跑一次，比较分数和成本。
  3. 保存优化后 JSON，检查里面指令和 demos 的变化。
  4. 换一个 LM 加载同一 JSON，验证“一次优化，多处部署”。

产出

优化前后分数对比 + 保存的 JSON 文件。

检验

你能解释 GEPA 为什么需要反馈，以及为什么反思模型和任务模型要分开。

6

端到端项目实战（指挥 agent）

核心问题：如何把签名、模块、工具、指标、优化器组合成一个完整程序？

选一个 BA 场景

  • 客服意图分类 + RAG 回答；
  • 合同实体提取 + 风险评估；
  • 用户反馈分类 + 摘要。

做什么

  1. 写“架构画布”（见后文）。
  2. 让 agent 按画布生成代码，要求插入调试语句。
  3. 你审查：签名命名、字段类型、模块选择、指标函数、数据划分、优化器预算。
  4. 跑基线 → 看中间结果 → 纠错 → 优化 → 保存。
  5. 记录每次纠错的原因和修改。

产出

一个可运行的端到端 DSPy 项目 + 纠错日志。

检验

你能不看代码细节，只看中间结果就定位问题。

7

复盘与“得意忘形”

核心问题：如何把 DSPy 变成你的架构直觉？

做什么

  1. 复盘 Day 1–6，整理“DSPy 架构画布”和“纠错检查表”。
  2. 拿一个全新业务需求，30 分钟内画出 DSPy 架构。
  3. 让 agent 生成代码，你只做审查和验收。
  4. 总结哪些 API 你根本不用记，哪些第一性原理必须记住。

产出

一页“DSPy 架构与纠错手册”。

检验

给你新需求，你能在 30 分钟内给出签名、模块、指标、优化器方案，并知道看哪里纠错。

中间结果阅读清单

纠错的核心——你必须亲自看这些

中间结果看什么能发现什么问题
lm.inspect_history() 实际提示词 签名命名、docstring、字段格式
result.trajectory ReAct 每步 thought/tool/observation 工具选择错误、循环过多
Evaluate.results 逐条预测与分数 指标是否合理、失败模式
prediction.get_lm_usage() token 和成本 是否太贵、是否缓存失效
保存的 JSON 优化后的指令和 demos 优化器改了什么、是否过拟合
print(prog.named_predictors()) 子模块树 优化器是否能看到所有子模块

纠错检查表

分数低时按顺序问

  1. 签名：字段名是否自解释？docstring 是否只写意图？
  2. 类型：该用 Literal 吗？该用 bool、float 吗？
  3. 模块：单步够吗？需要 ChainOfThought 吗？需要工具吗？
  4. 指标：有区分度吗？是否只看最终答案？需要 feedback 吗？
  5. 数据：.with_inputs() 是否泄漏答案？训练/验证是否分开？
  6. 优化器：预算够吗？trainset 和 valset 是否混用？
  7. LM 配置：任务模型和反思模型是否分开？温度是否合理？
  8. 缓存：是否因为缓存导致重复采样无效？
  9. 保存：加载 JSON 后是否重新配置了 LM？

与 Agent 协作的提示词模板

让 agent 生成 DSPy 代码时，你用这个模板

你是 DSPy 代码生成器。请按以下架构画布生成代码：
- 任务：
- 签名：输入字段、输出字段、字段类型、docstring
- 模块：选择 Predict / ChainOfThought / ReAct / 自定义 Module
- 工具：列出函数名、参数、docstring
- 数据：train/val/test 划分，with_inputs 字段
- 指标：函数签名和逻辑
- 优化器：类型、预算、trainset/valset
- 保存：路径和模式

要求：
1. 先输出架构图，再输出代码。
2. 插入调试语句：inspect_history、trajectory、Evaluate.results、get_lm_usage。
3. 每个模块加注释说明第一性原理。
4. 给出运行命令和预期中间结果。
工作方式

你审查架构图，不审查每一行代码。代码跑不通，让 agent 根据中间结果修。

人机分工：你需要手动做什么

你不需要手动打字，但你需要手动做架构判断、验收和纠错

核心结论

你不需要手动在 Python 文件里大量打字。但你需要手动做架构判断、验收和纠错。AI/agent 可以当你的“手”，替你写代码、运行、看日志、改代码。但你不能把“脑”和“眼”也交出去——否则你无法纠错，也无法得意忘形。

角色你（BA/架构师）AI/Agent（编码代理）

数据划分 决定 train/val/test，确认 .with_inputs() 不泄漏 写数据加载代码

为什么不能完全“让 AI 做事情”？

原因

因为 vibe coding 的瓶颈不是打字，是判断。

  • AI 可以写代码，但它不知道你的业务里“什么算对”。
  • AI 可以跑优化器，但它不知道指标有没有区分度、数据有没有泄漏。
  • AI 可以看 trajectory，但它不一定能判断“模型为什么调错工具”。
  • AI 可以改代码，但它可能把签名字段名改坏——而优化器不碰字段名，坏名字会永久拖累性能。

你一周后要能看懂中间结果，才能指挥 AI 修。如果你完全不做分析、不看结果，AI 改了三轮，你也不知道它是不是在瞎改。

你手动打字的唯一必要场景

  1. 改字段名和 desc——因为优化器不碰它们，AI 起名可能不准。
  2. 用自然语言精确描述指标逻辑——AI 写代码，但逻辑必须你把关。
  3. 记录纠错日志——这是你一周后“得意忘形”的资产。

推荐工作流

你指挥，AI 执行，你验收

你写自然语言架构画布
↓
AI 生成 prog.py + run.py
↓
Agent 运行，返回：
  • lm.inspect_history()
  • Evaluate.results 前 10 条
  • result.trajectory
  • get_lm_usage()
↓
你看中间结果，判断问题：
  • 字段名不好？→ 让 AI 改签名
  • 指标太松？→ 让 AI 改 metric
  • 模块不够？→ 让 AI 换 ChainOfThought
  • 数据泄漏？→ 让 AI 改 .with_inputs()
↓
AI 修改，再跑
↓
你验收：分数、成本、稳定性

一周里具体怎么操作

  • Day 1–2：让 AI 生成最小代码，你只改字段名，看 inspect_history。
  • Day 3–4：你画架构图，AI 写自定义 Module 和 ReAct，你只看 trajectory 和 Evaluate.results。
  • Day 5：你选优化器和预算，AI 跑，你看保存的 JSON 里指令和 demos 变了什么。
  • Day 6：端到端项目，你只写架构画布和验收标准，AI 写全部代码并运行，你纠错。
  • Day 7：拿新需求，你 30 分钟画架构，AI 生成，你验收。
工具建议

用 Jupyter/Colab，让 AI 直接生成并执行单元格。你用 Cursor、Claude Code、Codex 这类能跑代码的 agent，你负责看输出。

最终“得意忘形”检验

一周后，给你一个新业务需求

如果你能做到以下七步，你就已经“得意忘形”了：

  1. 30 分钟内画出 DSPy 架构画布；
  2. 写出签名和指标；
  3. 让 agent 生成代码；
  4. 跑通基线；
  5. 看懂中间结果；
  6. 定位问题并让 agent 修正；
  7. 选优化器并保存成果。
最终结论

你不需要手动在 Python 文件里打字。但你需要手动在脑子里做架构。AI 是你的手，不是你的脑。

vibe coding 的“vibe”来自你的判断力，不是来自放弃判断。API 细节全忘掉也没关系，因为你保留了最核心的东西：签名声明 what，模块定义 how，指标定义 better，优化器自动搜索，保存让成果成为资产。
